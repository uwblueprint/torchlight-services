# DB-01 — Core schema (12-table revision)

**Area:** API or database
**Depends on:** INFRA-01 (local Compose stack and live DB health)
**Blocks:** AUTH-01, BE-01, API-01 / API-02, FILE-01, OCR-01 / OCR-02, REVIEW-01, SHIFT-01 / INVOICE-01, REPORT-01, QA-API-01

## Context

`backend/app/db/models/` and `backend/alembic/versions/12adae7d6cbb_initial_schema.py`
implement a 24-table design. It was reviewed against the MVP and cut to 12 tables. The
removed tables carried per-field OCR provenance, an append-only expense history, funding
splits, a fiscal-period calendar, per-category cap overrides, and notifications — detail
that does not pay for itself at 36 participants and roughly 250 receipts a month.

This ticket implements the cut design. It supersedes the table list in
`docs/database-schema-proposal.md`; that document is kept as the record of what was
removed and why. Do not read its column lists as current.

Deliver one Alembic model set and one migration producing exactly the twelve tables
below. Preserve the constraints listed under "Invariants" — they are the reason the
tables exist, and several of them replace tables that were cut.

## Tables

`?` marks a nullable column. Every table has `id UUID PK` defaulting to
`gen_random_uuid()`.

### users
`display_name`, `email`, `role` (`admin|passport_worker`), `status`
(`invited|active|suspended|deactivated`), `deactivated_at?`, `created_at`, `updated_at`.

- `UNIQUE (email)`; `CHECK (email = lower(btrim(email)))`.
- `CHECK ((status = 'deactivated') = (deactivated_at IS NOT NULL))`.
- Supabase is the only identity provider; there is no `auth_provider`/`auth_subject`.
  **`email` is therefore the join key to Supabase Auth.** Document that renaming an
  email requires re-linking the account.

### participants
`display_name`, `client_code?`, `is_active` Boolean, `created_at`.

- `UNIQUE (client_code)`.

### participant_assignments
`participant_id` FK, `worker_id` FK, `assigned_at`, `ended_at?`.

- `CHECK (ended_at IS NULL OR ended_at >= assigned_at)`.
- Partial `UNIQUE (worker_id, participant_id) WHERE ended_at IS NULL` — one open
  assignment per pair. This is the authorization boundary; AUTH-01 depends on it.

### participant_budgets
`participant_id` FK, `fiscal_year` Integer, `managing_agency`, `total_budget`
Numeric(12,2), `admin_fee_percent` Numeric(5,2), `created_at`.

- `UNIQUE (participant_id, fiscal_year)`.
- `CHECK (total_budget >= 0)`, `CHECK (admin_fee_percent BETWEEN 0 AND 100)`.

### category_allocations
`participant_budget_id` FK, `category_id` FK, `allocated_amount` Numeric(12,2),
`projected_amount` Numeric(12,2).

- `UNIQUE (participant_budget_id, category_id)`.
- `CHECK (allocated_amount >= 0)`, `CHECK (projected_amount >= 0)`.
- Rows are **materialized** when a budget is created, seeded from
  `funding_categories.default_annual_cap`. There is no "absent means default" rule
  any more, so a balance query never falls back.

### funding_categories
`code`, `name`, `default_annual_cap` Numeric(12,2), `active` Boolean.

- `UNIQUE (code)`.

### funding_subcategories
`category_id` FK, `name`, `active` Boolean.

- `UNIQUE (category_id, name)`.

### expenses
`participant_id` FK, `fiscal_year` Integer, `receipt_id?` FK, `category_id?` FK,
`subcategory_id?` FK, `other_category_desc?`, `submitted_by_id?` FK,
`source_kind` (`worker|admin|day_program_invoice|import|other`), `vendor_name?`,
`receipt_number?`, `start_date`, `end_date?`, `ticket_count?`, `total_amount`
Numeric(12,2), `covered_amount` Numeric(12,2), `out_of_pocket_amount` Numeric(12,2),
`status` (`draft|awaiting_worker_confirmation|confirmed|rejected|voided`),
`review_status` (`not_required|pending|reviewed|needs_correction`), `reviewed_by_id?` FK,
`reviewed_at?`, `review_note?`, `family_informed_note?`, `invoice_status`,
`invoice_payer_name?`, `created_at`.

- `CHECK (covered_amount + out_of_pocket_amount = total_amount)` — replaces
  `expense_funding_splits`.
- `CHECK ((reviewed_by_id IS NULL) = (reviewed_at IS NULL))`.
- `CHECK (total_amount >= 0)`, `CHECK (end_date IS NULL OR end_date >= start_date)`,
  `CHECK (ticket_count IS NULL OR ticket_count >= 0)`.
- `CHECK (other_category_desc IS NULL OR btrim(other_category_desc) <> '')`.
- `CHECK (status <> 'confirmed' OR total_amount > 0)`.
- Query index `(participant_id, fiscal_year, category_id, status)` and
  `(review_status, created_at)` for the review queue.

### receipts
`participant_id` FK, `uploaded_by_id` FK, `storage_key`, `content_type`,
`ocr_status` (`pending|succeeded|failed|skipped`), `ocr_confidence?`
Numeric(5,4), `ocr_extracted_data?` JSONB, `created_at`.

- `UNIQUE (storage_key)`.
- `CHECK (ocr_confidence IS NULL OR (ocr_confidence >= 0 AND ocr_confidence <= 1))`.
- `expenses.receipt_id` is many-to-one, so one invoice can back several expenses
  (the two-participant case). Multi-page uploads must be one object per receipt.

### shift_logs
`participant_id` FK, `worker_id` FK, `shift_start?`, `shift_end?`, `mileage_km?`
Numeric(10,2), `notes?`, `status`, `created_at`.

- `CHECK (shift_end IS NULL OR shift_start IS NULL OR shift_end > shift_start)`.
- `CHECK (mileage_km IS NULL OR mileage_km >= 0)`.
- At least one of the shift or mileage part must be present:
  `CHECK (shift_start IS NOT NULL OR mileage_km IS NOT NULL)`.
- Both nullable parts are required so a mileage-only trip with no support hours is
  representable. Do not invent mileage rates.

### activity_plans
`participant_id` FK, `created_by_user_id` FK, `fiscal_year` **Integer**, `title`,
`planned_for` Date, `status`, `created_at`, `updated_at`, `expires_at?`.

- `fiscal_year` is Integer for consistency with `participant_budgets` and `expenses`;
  the design sketch typed it UUID FK by mistake. Confirm before migrating.
- No line items: a plan is a dated header, not a costed estimate.

### audit_events
`actor_user_id?` FK, `action`, `entity_type`, `entity_id?` UUID, `occurred_at`,
`request_id?`, `safe_details` JSONB default `'{}'`.

- Append-only. Index `(entity_type, entity_id, occurred_at)` and
  `(actor_user_id, occurred_at)`.
- This is now the **only** history table. Review decisions, corrections, and
  voids must be written here, since `expense_events`, `expense_reviews`, and
  `expense_adjustments` no longer exist.

## Seeds

- `funding_categories`: 19 rows — the Ministry PDF's numbered items 1–12 and 14–19,
  plus "Other types, please specify". Confirm the transcribed names and codes against
  the source before seeding; the 18-vs-19 count in `backend/README.md` and the model
  docstring disagree and must be resolved here.
- `funding_subcategories`: per category, not global.

No participant, budget, expense, or receipt data is seeded.

## Recorded decisions

These were made during the cut review; implement them, do not re-open them
casually.

1. Fiscal year is an integer column. No `fiscal_periods` table, so nothing records
   when a year opened or closed. `fiscal_year` must be **derived from
   `start_date`** in the service layer, never accepted from the client, or the three
   copies (budget, expense, plan) will drift.
2. Coverage is two columns on `expenses`, not a splits table. Who paid the
   out-of-pocket portion is a note, not data.
3. Hours and mileage share `shift_logs`.
4. Receipt files and OCR output share `receipts`, with `ocr_extracted_data` as one
   JSONB blob. There is no per-field provenance and therefore no FK from an expense
   to "the candidate it was confirmed from".
5. `activity_plans` has no lines.
6. `audit_events` is the single history table.

## Accepted trade-offs

Recorded so they are not rediscovered as bugs:

- `receipts.participant_id` and `expenses.participant_id` can disagree when a receipt
  is shared. The receipt's participant is bookkeeping; the expense is authoritative.
- No adjustment ledger: a wrong confirmed expense is voided and re-entered, not
  edited. Enforce this in the API layer (API-02), since the schema cannot.
- `funding_subcategories` has no `code`; renaming one changes historical display.

## Open decisions

1. **Admin fee.** Does `total_budget` include the admin fee? Must
   `SUM(category_allocations.allocated_amount)` equal `total_budget`, or
   `total_budget * (1 - admin_fee_percent/100)`? One answer is needed before writing
   the CHECK or the BE-01 reconciliation query. Proposed default: `total_budget` is
   gross, allocations sum to `total_budget * (1 - admin_fee_percent/100)`.
2. **`expenses.category_id` nullability.** The sketch shows it nullable. If it stays
   nullable, the balance query must skip unclassified rows and the "category always
   required" rule from the old schema is gone. If it is required, an unclassified
   expense must be created against the "Other types" category instead.

## Verification

- `alembic upgrade head` on a clean database, then `alembic check` reports no
  outstanding model/migration drift.
- `alembic downgrade base && alembic upgrade head` round-trips.
- `pytest -q` passes.

Manual SQL against a scratch database:
- `INSERT` an expense with `covered_amount` + `out_of_pocket_amount` not equal to
  `total_amount` → rejected.
- `INSERT` with `reviewed_by_id` set and `reviewed_at` NULL → rejected.
- Two open `participant_assignments` for the same worker and participant → rejected.
- Assert `SELECT count(*) FROM information_schema.tables WHERE table_schema='public'
  AND table_name <> 'alembic_version'` returns 12.
