# FE-10 — Participant workspace (`/admin/participants/[id]`)

**Area:** Admin portal
**Depends on:** API-01, API-02, BE-01, AUDIT-LOG-01, DB-01, FE-03, FE-09
**Blocks:** FE-11, FE-12 (they link back here)

## Context

This is the admin's working view of one person: profile, annual funding setup, category
allocations, the expense log, notes, and receipt history. PassportONE's client Expense Log
is the reference for arrangement, not a template to copy blindly.

The stub uses a static demo id and renders placeholder tables. It is also the only place
annual budgets and category allocations can be created, so it carries the two open DB-01
decisions: admin-fee treatment and whether `category_id` is optional on expenses.

## Current stub

`src/app/admin/participants/[id]/page.tsx` — participant information form, funding
allocations table, expense log, notes table, with a static `participant-id` param.

## Deliverables

1. **Load by route id** — treat the segment as a UUID, fetch the participant, call
   `notFound()` for an unknown or unavailable record, and show an authorization error for a
   forbidden one. No demo fallback.
2. **Profile** — display name, client code, active flag. Save through the API, show field
   errors inline, and refetch after save. Do not render edit controls for fields the API
   does not accept.
3. **Annual budget** — per fiscal year: `total_budget`, `admin_fee_percent`, and
   `managing_agency`. Creating a budget materializes `category_allocations` rows from
   `funding_categories.default_annual_cap` (DB-01). Show the allocation total the server
   computes; the admin-fee question is still open, so the UI must not assert that
   allocations equal `total_budget` or `total_budget * (1 − fee)`.
4. **Category allocations** — editable `allocated_amount` and `projected_amount` per
   category, money strings only, with the server's validation surfaced. `projected_amount`
   is a planning figure, not derived from expenses.
5. **Expense log** — per fiscal year, with date, description, category, amount, coverage
   split, source, status, and receipt. Read-only here except for actions the approved
   workflow defines. A confirmed expense is not editable: void and re-enter (DB-01), and
   the UI should say so when an admin tries.
6. **Notes and follow-up** — dated notes with author and follow-up status, recorded through
   the API and visible in FE-08's inbox. Notes about family/caregiver conversations include
   who was informed and when, without asserting an acknowledgment rule.
7. **Receipt history** — list of receipts with date, amount, and status; opening one goes to
   the review workspace (FE-11) or the signed download, never a public URL.
8. **States** — 404, 403, no budget for the selected year, no expenses, save conflict,
   loading skeleton per panel.

## Data

Confirm in API-01 / API-02:

- `GET /api/v1/participants/{id}`
- `GET /api/v1/participants/{id}/balances?fiscal_year=`
- `GET /api/v1/participants/{id}/expenses?fiscal_year=&cursor=`
- `PUT /api/v1/participants/{id}`
- `PUT /api/v1/participants/{id}/budgets/{fiscal_year}`
- `PUT /api/v1/participants/{id}/allocations` (allocation rows)
- `GET /api/v1/participants/{id}/notes`

## Out of scope

- Bulk budget copy from a prior year, unless it becomes an agreed workflow; do not add it
  speculatively.
- Generating invoices or exports: FE-12 and FE-13.
- Worker access; workers never see this profile.

## Acceptance criteria

- `/admin/participants/<random uuid>` renders the not-found state.
- Saving a profile field persists across a refresh and produces an audit event.
- Creating a budget for a year with no rows produces one allocation row per seeded
  category; creating a second budget for the same participant and year is rejected with a
  readable conflict (`UNIQUE (participant_id, fiscal_year)`).
- Allocation amounts accept `"1234.50"` and reject `"1234.567"`, `"-1"`, and letters before
  submit; the input never turns into a float.
- Changing `admin_fee_percent` does not make the screen claim a rule the ticket has not
  settled.
- A confirmed expense offers no edit action; the void/re-enter path is offered instead, and
  it produces an audit event.
- The page never renders data for a participant the admin is not authorized to see.
