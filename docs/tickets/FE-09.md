# FE-09 — Participant directory (`/admin/participants`)

**Area:** Admin portal
**Depends on:** API-01, AUTH-01, DB-01, FE-03, FE-08
**Blocks:** FE-10 (directory is the way in)

## Context

Admins look up a participant by name or client code and open their workspace. PassportONE's
expense log shows allotment, spent, and available across the current and prior two years,
which is the reference for the detail screen behind this list.

The stub mixes a search form, a directory table, and a requirements checklist. Only the
first two belong here; the checklist is implementation notes and should disappear rather
than ship to users.

## Current stub

`src/app/admin/participants/page.tsx` — search and status filter, a six-column directory
table, a links panel, and an expense-log checklist.

## Deliverables

1. **Search** — server-side `q` matching display name and client code, debounced, with the
   term in the URL (`?q=&status=`). Clearing restores the full list without a full page
   reload.
2. **Status filter** — active, inactive, all, matching `participants.is_active`.
3. **Directory table** — participant, client code, annual allocation for the selected
   fiscal year, managing agency, status, and an explicit "Open" link per row. Row click
   may also navigate, but the link must exist for keyboard and middle-click.
4. **Paging** — cursor-based once the roster grows; 36 participants fit on one page today,
   so render a single page plus `total` and add paging only if the API returns a cursor.
5. **New participant** — only if the approved workflow includes admin creation. If it does,
   route to FE-10's creation state; do not invent a second form. If not, omit the action.
6. **States** — no results for a search (with the query echoed and a clear-search action),
   no participants at all (distinct from no results), error with retry, loading rows.
7. **Remove the checklist panel** — implementation notes do not belong in the shipped UI.

## Data

- `GET /api/v1/participants?q=&status=&cursor=` → `{ items, total, next_cursor }`.
- Annual allocation comes from the participant's budget for the requested year; if it is not
  included in the list payload, the column renders "not set" rather than silently omitting
  the participant.

## Out of scope

- Editing participant fields, budgets, or allocations: FE-10.
- Bulk actions, CSV import, or deletion.
- Worker access to this route.

## Acceptance criteria

- Searching a client code returns that participant; searching a nonexistent term shows the
  empty-search state, not an empty table with headers and no explanation.
- The filter and query survive a page refresh and the back button.
- A participant with no budget for the year shows "not set" in the allocation column, not
  `$0.00`.
- Opening a row reaches `/admin/participants/{id}`; an unknown id there produces the 404
  state, not a crash.
- The checklist panel and its TODO badge are gone from the rendered page.
- A worker hitting this URL is redirected by the server guard.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against a local API with
synthetic participants: search by name and code, filter each status, no-results, empty
database, and keyboard navigation through the table.
