# FE-03 — Sign-in, session, and role routing (`/login`, `/`)

**Area:** Worker portal
**Depends on:** AUTH-01, FE-02
**Blocks:** Every authenticated FE screen (FE-04 – FE-13)

## Context

The research flow has one shared login that lands admins and passport workers in different
portals. Today `/login` is a stub with disabled fields, `/` is a developer implementation
map, and `worker` and `admin` layouts render a shell for anyone who types the URL. There is
no session, no role check, and no way to sign out.

Supabase Auth is the provisional direction (decisions.md 8). Roles are **not** implied by
an email domain: the API resolves the role from `users` and enforces it per request.

## Current stub

`src/app/login/page.tsx` (disabled form plus link list), `src/app/page.tsx` (route map),
and the two `layout.tsx` files, which currently guard nothing.

## Deliverables

1. **Sign-in form** — work email and password, submitted to the AUTH-01 flow. Show invalid
   credentials, unverified invite, suspended account, and network failure as distinct,
   readable states. Never echo the password back.
2. **Role-aware landing** — after sign-in, fetch the server-resolved role and redirect:
   admin → `/admin/dashboard`, passport worker → `/worker/dashboard`. Unknown or
   unprovisioned role → a clear "account not set up" page, not a redirect loop.
3. **`/` behavior** — replace the implementation map with a redirect by role once FE-04
   and FE-08 exist. Until then, link the map from the login stub only.
4. **Route protection** — unauthenticated requests to `/worker/*` or `/admin/*` redirect to
   `/login` with the intended path preserved, then return there after sign-in. Implement
   the guard with the session mechanism AUTH-01 chooses; read the bundled Next 16 docs
   before picking middleware or proxy conventions, both of which changed recently.
5. **Role mismatch** — a worker opening an `/admin/*` URL is redirected to their own
   dashboard with a one-line explanation; it is not treated as a login failure.
6. **Sign-out** — visible in the portal shell, clears the session server-side, and the
   back button does not restore protected content.
7. **Session expiry** — refresh where possible, otherwise redirect to `/login` with a
   message; in-flight saves must not silently fail.

## Out of scope

- MFA, password policy, SSO, and org-domain allowlist decisions: AUTH-01.
- Participant or caregiver accounts.
- Building an invitation acceptance page beyond what FE-02 and AUTH-01 define.

## Acceptance criteria

- Visiting `/admin/participants` signed out redirects to `/login`, and signing in as an
  admin returns to that exact path.
- A signed-in worker requesting `/admin/participants` lands on `/worker/dashboard` with an
  explanation; no admin data renders even briefly.
- No protected content flashes before the redirect.
- Signing out then pressing back does not show the previous protected page.
- The session is not readable from `localStorage`.
- An account with no `users` row and no role gets the explicit "not set up" page.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual walkthrough with two synthetic
accounts (admin, worker) against a local API or the AUTH-01 stub: deep link, role mismatch,
sign-out, expiry. Check the server-rendered HTML for the signed-out case, not just the
browser view.
