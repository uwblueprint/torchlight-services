# FE-11 — Receipt follow-up & categorization (`/admin/ocr-review`)

**Area:** Admin portal
**Depends on:** REVIEW-01, FILE-01, OCR-02, AUDIT-LOG-01, DB-01, FE-03
**Blocks:** FE-13 (archives read reviewed receipts)

## Context

Admins work through unclear or incomplete receipts, fix the details, choose the PassportONE
category, and leave an audit trail. Research notes are explicit that no AI decides this;
OCR output is advisory and a person confirms every value (decisions.md 5).

The stub has a filter form, an empty queue table, and a checklist describing the review
workspace. The queue and the workspace are the deliverables; the checklist should be
replaced by the actual workspace.

## Current stub

`src/app/admin/ocr-review/page.tsx` — filters, a seven-column queue table, and a review
workspace checklist.

## Deliverables

1. **Queue** — filter by participant, receipt date, `review_status`
   (`pending`, `reviewed`, `needs_correction`), and category. `not_required` records never
   appear. Filters live in the URL, and the queue paginates with a cursor.
2. **Queue rows** — uploaded date, participant, vendor or description, amount, category,
   issue (missing field or low `ocr_confidence`), assigned reviewer, and status. Amounts are
   strings; confidence is a number from 0 to 1, displayed as a label alongside the value,
   never as colour alone.
3. **Review workspace** — receipt preview beside editable metadata, on one screen at
   desktop width:
   - signed, short-lived preview URL for PDF and image receipts; Word documents download
     rather than render;
   - editable date, amount, vendor, category, subcategory (conditional), and note;
   - participant and expense link;
   - save, and "return to queue", with no automatic approval or posting.
4. **Reviewer attribution** — saving sets `reviewed_by_id` and `reviewed_at` together;
   the schema rejects one without the other. The UI shows the current reviewer and the
   resulting status.
5. **Audit** — every correction writes an `audit_events` row with actor, action, entity, and
   safe details (no receipt bytes, no OCR text, no secrets). The workspace shows the
   record's prior review entries.
6. **Follow-up** — mark `needs_correction` with an owner and note for items awaiting the
   family or worker, and surface them in FE-08's inbox.
7. **States** — empty queue, no results for filters, preview unavailable, file missing from
   storage, save conflict because another admin reviewed it first, and a receipt with no
   linked expense.

## Data

Confirm in REVIEW-01:

- `GET /api/v1/receipts?participant_id=&review_status=&category_id=&cursor=`
- `GET /api/v1/receipts/{id}` with a signed preview URL
- `PATCH /api/v1/expenses/{id}` for corrections (API-02 owns the write rules)
- `POST /api/v1/expenses/{id}/review` for status transitions and notes

## Out of scope

- Improving extraction accuracy or OCR thresholds: OCR-02.
- Bulk approval, auto-categorization, or any "accept all" action.
- Deleting receipts; retention policy is unresolved.

## Acceptance criteria

- The queue excludes `not_required` expenses even when requested through the URL.
- A low-confidence receipt appears in the queue with a text issue label and a readable
  confidence value.
- Saving a correction updates the row, sets both reviewer fields, and creates exactly one
  audit event.
- Two admins editing the same expense: the second save shows a conflict and offers reload
  instead of silently overwriting.
- A Word receipt offers download, not a broken preview.
- No receipt image, vendor, or amount from source documents is used as a fixture.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual with synthetic PDFs and images
against a local API: filter combinations, low confidence, correction save, conflict, missing
file, and audit entry. Check the workspace at 1280px and with keyboard only.
