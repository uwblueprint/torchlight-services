# FE-04 — Worker funding & activity (`/worker/dashboard`)

**Area:** Worker portal
**Depends on:** AUTH-01, API-01 (participant reads and balances), DB-01, FE-03
**Blocks:** FE-05, FE-06, FE-07 (they receive the selected participant from this screen)

## Context

This is a passport worker's home screen. They pick one of their assigned participants,
see what the annual budget looks like by category, and read a bank-statement-style history
of expenses and receipts so they can plan the next purchase or work session. The stub lists
the right pieces but every value is `—` and the participant search is disabled.

The scoping rule is the important part: a worker sees only their open
`participant_assignments`. The API enforces that; this screen must not offer a filter that
implies broader access.

## Current stub

`src/app/worker/dashboard/page.tsx` — participant search, three metrics, a combined
balance/history table with seven columns, and quick-action links.

## Deliverables

1. **Participant switcher** — assignment-scoped list with search by name or client code.
   With one assignment, select it automatically. With none, show an empty state explaining
   that an admin must assign a participant. Put the selection in the URL
   (`?participant=<uuid>`) so refresh and back keep it.
2. **Fiscal year selector** — current and prior two fiscal years (the stub's requirement).
   Default to the current year and keep it in the URL beside the participant.
3. **Summary metrics** — allocated, spent, and available to plan for the selected
   participant and year, from the balances endpoint. Server-computed; render as money
   strings and never re-sum client-side.
4. **Category balances** — one row per materialized `category_allocations` row:
   `category_code`, `category_name`, `allocated_amount`, `projected_amount`,
   `spent_amount`, `remaining_amount`. Show a negative remainder as negative (DB-01: no
   adjustment ledger, overspend is real data), not clamped to zero.
5. **Transaction history** — expenses for the participant and year: date, vendor or
   description, category, amount, coverage split, status, receipt access. Statuses include
   `draft`, `awaiting_worker_confirmation`, `confirmed`, `rejected`, `voided`; show them
   literally rather than collapsing into "done".
6. **Quick actions** — add expense, coverage calculator, hours/mileage, carrying the
   selected participant and fiscal year into those routes.
7. **States** — no assignments, participant with no budget for that year (say "no budget
   recorded", not `$0.00`), API error with retry, loading skeleton.

## Data

Proposed contracts, confirmed in API-01:

- `GET /api/v1/participants` — assignment-scoped, `{ "items": [...] }`.
- `GET /api/v1/participants/{id}/balances?fiscal_year=2026` — category rows.
- `GET /api/v1/participants/{id}/expenses?fiscal_year=2026` — paged ledger rows.

Pending expenses are **not** part of `spent_amount`. If the UI needs them, they arrive as a
separate field; do not add them by hand.

## Out of scope

- Editing expenses or receipts; corrections belong to the review and expense screens.
- Worker-facing receipt upload: FE-05.
- Export or invoice views: admin scope.
- Any participant detail beyond label and client code.

## Acceptance criteria

- A worker with two assignments sees exactly those two; a third participant is absent even
  when requested via URL, and the API's 403 renders as an error state rather than an empty
  table.
- Switching participant refetches balances and history for the new selection; the URL
  reflects both participant and year.
- The three metrics equal the server totals; a category row's `remaining_amount` equals
  `allocated_amount − spent_amount` as returned, and negative values are visible.
- A year with no budget shows an explicit empty state, not zero balances.
- Row-level receipt access opens the receipt only when the expense has one; otherwise the
  cell says "no receipt".
- The page is usable at 375px wide with the table scrollable rather than clipped.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against a local API with two
synthetic participants: check authorization with an unassigned participant id, the
fiscal-year switch, an empty year, and a negative remainder. Do not use real records.
