# FE-02 — Team directory & worker onboarding (`/admin/team`)

**Area:** Admin portal
**Depends on:** AUTH-01, DB-01 (`users`, `participant_assignments`)
**Blocks:** FE-03 (an invited account has to exist before sign-in can be tested), FE-10
(assignment management links here)

## Context

Torchlight staff manage access from the Team directory: invite a passport worker or admin,
review account and training state, and follow up on anyone who is not fully onboarded. The
supplied Beacon prototype's **Team** page and **Add team member** modal are the visual
target, with the per-person onboarding checklist on a member detail page.

The old `/onboarding` screen was a single invite form beside hardcoded checklist cards. It
did not match the Team directory, did not separate workers from admins, and exposed every
checklist at once. This ticket replaces it with the team-management flow. `/onboarding`
redirects to `/admin/team` so existing links continue to work.

This flow is admin-operated. There is no public sign-up: a worker cannot create their own
account, choose their role, or assign themselves a participant (decisions.md 8).

## Deliverables

1. **Team directory** — `/admin/team` with Passport workers/Admins tabs and counts, search
   by name or email, sorting, an Add team member action, and rows that open
   `/admin/team/[id]`.
2. **Add team member modal** — role (`passport_worker` or `admin`), full name, and email.
   Submit through AUTH-01's invite endpoint. Normalize email to lowercase and trim before
   sending; `users` enforces `email = lower(btrim(email))`. Disable submit until the required
   fields are present.
3. **Inline validation** — required fields, email shape, duplicate account (surface the
   API's conflict), and a domain that fails AUTH-01's approved allowlist. Errors belong next
   to the field, with a summary that receives focus on submit.
4. **Role-specific modal content** — passport-worker accounts show the assignment handoff;
   admin accounts show the permission preset/area matrix as a non-functional preview until
   AUTH-01 defines enforcement. The modal must not imply that unsaved permissions are real.
5. **Member detail and data-driven checklist** — `/admin/team/[id]` shows account status
   (`invited`, `active`, `suspended`, `deactivated`), role, open
   `participant_assignments`, and training acknowledgment from the API. No local toggles
   that pretend completion.
6. **Assignment handoff** — link to the participant workspace (FE-10) for assigning or
   removing participants. Do not duplicate that edit form here until an assignment API is
   agreed.
7. **Training acknowledgment** — record who acknowledged which material and when, as an
   audit event (AUDIT-LOG-01), not a checkbox in local state.
8. **Empty, loading, and error states** — no workers/admins yet, no search results, invite
   failed, resend available per AUTH-01's flow, and an API load failure.

## Out of scope

- Password setting, MFA policy, email templates, permission enforcement, and the invite
  transport: AUTH-01.
- Participant profile, budget editing, and assignment management: FE-10.
- Any self-service path for participants or caregivers.

## Acceptance criteria

- An admin can open `/admin/team`, switch between worker and admin lists, search, and open
  a member detail page.
- An admin can invite a worker from the modal and sees the new `invited` record in the
  directory without a page reload showing stale data.
- The invite modal disables sending until full name and email are present, and an invited
  address that already exists is rejected with a readable conflict.
- A non-admin who reaches `/admin/team` or `/admin/team/[id]` is denied by the
  server-rendered guard, even when typing the URL directly.
- The member checklist reflects server state: a worker whose invite is pending does not show
  as onboarded.
- Resending an invite and recording training acknowledgment refresh the directory and member
  detail; training creates an audit event with actor and timestamp.
- Admin permission controls are visibly non-functional until AUTH-01 defines them, and
  submitting an invite does not pretend to save permissions.
- No email address, name, or role from source documents appears in fixtures.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual: invite with a synthetic
address against a local API; confirm duplicate rejection, non-admin denial, search/tabs,
and that the checklist changes only when the API says so. Do not send real email.
