# FE-07 — Coverage calculator (`/worker/calculator`)

**Area:** Worker portal
**Depends on:** BE-01, API-01, DB-01, FE-04
**Blocks:** FE-05 uses the same calculation endpoint for its preview.

## Context

Before buying something, a worker estimates how much Passport would cover and how much the
participant or family would pay. This is a planning view. It must never read as an approval,
and it must use the same arithmetic as the ledger so the estimate and the saved expense
agree to the cent.

The stub has the right inputs and three result metrics, all inert.

## Current stub

`src/app/worker/calculator/page.tsx` — participant, fiscal year, category, planned amount,
and a coverage result panel.

## Deliverables

1. **Inputs** — participant from open assignments, fiscal year (current or prior one),
   category from the seeded catalog, and a planned amount entered as a decimal string. Show
   the category's remaining allocation and cap headroom beside the field so the worker can
   judge before calculating.
2. **Submit to the server** — call BE-01's endpoint with `{ participant_id, fiscal_year,
   category_id, requested_amount }`. No coverage math in the browser, not even a preview of
   the split.
3. **Result** — requested, covered, out of pocket, remaining allocation after the estimate,
   and remaining category headroom when a cap applies. Render money strings; if the split
   does not reconcile to the request, treat it as a contract error, not a display rounding
   problem.
4. **Assumptions** — state what the number depends on: fiscal year, category, current
   confirmed spend, and that caps and fees are unconfirmed policy. Prominent
   "estimate only — not an approval" copy is required on the result, not buried in a
   footnote.
5. **Handoff** — an action that carries participant, category, and amount into FE-05. It
   must not create an expense by itself.
6. **Validation** — zero, negative, non-numeric, and more than two decimals are rejected
   inline; amounts are sent as strings. A request the server rejects as too large for the
   column shows a readable message.
7. **States** — no assignments, category with no allocation row for that year (explain,
   don't assume zero), participant over budget, API failure.

## Data

- `POST /api/v1/coverage` — proposed; BE-01 owns the contract. Response carries
  `requested_amount`, `covered_amount`, `out_of_pocket_amount`,
  `remaining_allocated_budget`, `remaining_category_cap`.
- `GET /api/v1/participants/{id}/balances?fiscal_year=` for the context figures.

## Out of scope

- Saving or approving the result.
- Editing category caps or budget allocations.
- Eligibility rules beyond what BE-01 encodes; the screen never asserts that an expense
  qualifies.

## Acceptance criteria

- For a synthetic case, the displayed split equals BE-01's result exactly, including the
  `10.01 → 10.00 + 0.01` style cases covered by the calculator tests.
- Changing any input clears the previous result rather than showing a stale estimate.
- No network write happens on calculate (check the request log: GET/POST to coverage only,
  no expense created).
- A participant with no allocation for the year shows an explanatory state, not `$0.00`.
- Over-budget input produces a covered amount of zero and a visible out-of-pocket figure,
  with copy that does not imply the purchase is blocked or approved.
- Keyboard-only completion works; the result is announced via `aria-live`.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against BE-01 with the
synthetic cases from its tests: exact split, exhausted category, zero amount, oversized
amount, no allocation. Confirm the estimate and a subsequent FE-05 save produce the same
split.
