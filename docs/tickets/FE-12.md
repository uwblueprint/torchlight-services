# FE-12 — Overages & invoice tracking (`/admin/invoicing`)

**Area:** Admin portal
**Depends on:** INVOICE-01, API-02, AUDIT-LOG-01, DB-01, FE-03
**Blocks:** None. FE-13 may reference invoice status.

## Context

Some expenses are not fully covered by Passport. The family may pay, a partner organization
may pay, or Torchlight absorbs the cost, and Janella currently tracks those invoices by
hand. Research notes confirm the app tracks amounts and status only — it never collects or
moves money.

`expenses` already carries the split: `covered_amount` plus `out_of_pocket_amount` equals
`total_amount`, so "uncovered" is a subtraction the server performs. The stub's queue and
form describe the right workflow with nothing behind them.

## Current stub

`src/app/admin/invoicing/page.tsx` — uncovered-cost queue, invoice tracking form, and a
boundary checklist.

## Deliverables

1. **Uncovered queue** — confirmed expenses with `out_of_pocket_amount > 0`, showing date,
   participant, expense, Passport-covered amount, uncovered amount, payer, invoice status,
   and a follow-up marker. Server computes the uncovered figure; the client never subtracts
   money strings.
2. **Filters** — fiscal year, participant, invoice status, and payer, in the URL and
   paginated.
3. **Invoice record** — per expense: responsible payer, invoice amount, invoice status
   (`draft`, `sent`, `resolved`, `written_off`), and a family/caregiver communication note
   with who was informed and when. Save through the API.
4. **Payer list** — the stub proposes family, partner organization, Torchlight absorbs, and
   to-be-determined. That list is **unconfirmed**; keep it configurable on the server and
   render whatever the API returns rather than hardcoding four values in the UI.
5. **Status history** — every status change appears with actor and timestamp, read from
   `audit_events`. The screen does not maintain its own history array.
6. **States** — no uncovered expenses, no invoices yet, save conflict after another admin
   updated the record, and an expense whose status changed to `voided` after an invoice was
   drafted (surface it; do not silently delete the invoice).
7. **Boundary copy** — the screen states plainly that it records an amount owed and its
   status; it does not send an invoice, process a payment, or notify the family
   automatically.

## Data

Confirm in INVOICE-01:

- `GET /api/v1/expenses?has_out_of_pocket=true&fiscal_year=&invoice_status=&cursor=`
- `GET /api/v1/invoices?status=&cursor=`
- `PUT /api/v1/expenses/{id}/invoice` — payer, amount, status, note
- `GET /api/v1/audit-events?entity_type=expense&entity_id={id}`

## Out of scope

- Payment processing, receipts for payments, refunds, or accounting-system sync.
- Auto-notifying the family by email or SMS.
- Deciding the payer policy; INVOICE-01 must record it first.

## Acceptance criteria

- The queue shows only confirmed expenses with a positive out-of-pocket amount; a fully
  covered expense never appears.
- The uncovered amount equals the server value for every row and reconciles with the
  expense's split.
- Saving a payer, amount, and status persists across refresh and produces an audit event.
- Changing status shows the new value with actor and timestamp in the history panel.
- An expense voided after invoice creation remains visible with a visible warning.
- No dollar amount from source documents is used in fixtures.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against a local API with
synthetic expenses: fully covered, partly covered, voided after invoicing, each status
transition, and a concurrent edit.
