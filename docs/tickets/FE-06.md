# FE-06 — Hours & mileage (`/worker/shifts`)

**Area:** Worker portal
**Depends on:** SHIFT-01, DB-01 (`shift_logs`), FE-03, FE-04
**Blocks:** None. Reporting reads shift data later (FE-13).

## Context

Passport workers record support hours and mileage for the participants they work with.
Research notes call for start/end times, mileage, and a work note, but say nothing about
meal eligibility, mileage rates, rounding, or reimbursement — so this screen records facts
and calculates nothing.

DB-01 puts hours and mileage in one `shift_logs` table with both parts nullable, requiring
only that at least one is present. A mileage-only trip with no support hours is valid.

## Current stub

`src/app/worker/shifts/page.tsx` — a six-field "new work record" form and a read-only table
of the worker's records, with a callout saying no rate or rule is assumed.

## Deliverables

1. **Entry form** — participant (open assignments), work date, start time, end time,
   mileage in km, and an optional note. Validate before submit: end after start on the same
   record, mileage `>= 0`, and at least one of a shift pair or mileage.
2. **Mileage-only and shift-only paths** — both save. The form must not require end time
   when the worker only drove, and must not require mileage for a support session.
3. **No derived money** — no rate, reimbursement, or meal calculation appears anywhere,
   including helper text. Show entered hours and km as recorded.
4. **Record list** — the worker's own rows, newest first, with date, participant, start,
   end, computed duration for display, mileage, note, and status. Duration formatting is
   display only and never stored or sent.
5. **Correction path** — editing an existing record follows the workflow SHIFT-01 defines.
   If SHIFT-01 has not settled whether a submitted log is editable or voided and re-entered,
   this ticket stays blocked rather than picking one.
6. **States** — no assignments, no records yet, save failure with retained input, invalid
   time range, and a warning when the shift crosses midnight (the schema compares
   timestamps, so this must be represented unambiguously).

## Data

Proposed; confirm in SHIFT-01:

- `GET /api/v1/shifts?fiscal_year=2026` — worker-scoped.
- `POST /api/v1/shifts` — `participant_id`, `shift_start`, `shift_end`, `mileage_km`,
  `notes`.
- `PATCH /api/v1/shifts/{id}` — only if the approved lifecycle allows corrections.

Times are sent as full ISO 8601 timestamps with an offset; the browser's local zone is
used and displayed with the zone named, so a log written in one timezone does not silently
shift.

## Out of scope

- Mileage rates, meal rules, overtime, rounding, or reimbursement totals.
- Admin views of shift data.
- Payroll export.

## Acceptance criteria

- A record with start and end but no mileage saves and appears in the list.
- A record with mileage but no times saves.
- A record with neither is blocked client-side and rejected by the API when forced.
- End time before start time shows a field error and does not submit.
- Negative mileage is blocked.
- A worker cannot see another worker's rows, including by editing the URL.
- No screen in this flow shows a dollar amount.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against a local API with two
synthetic workers: each field combination, overnight entry, invalid range, and the
cross-worker check.
