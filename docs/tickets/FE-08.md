# FE-08 — Admin overview (`/admin/dashboard`)

**Area:** Admin portal
**Depends on:** API-01, API-02, AUDIT-LOG-01, DB-01, FE-03
**Blocks:** None; links into FE-09, FE-10, FE-11, FE-12.

## Context

The office needs one screen that answers "what is the state of the whole caseload right
now": how many participants, how much is allocated and spent, what needs follow-up, and
what changed recently. The stub names all four panels and leaves every count blank.

This is also where the audit trail becomes visible to staff for the first time. It reads
`audit_events`, the single history table (DB-01), not a parallel activity log.

## Current stub

`src/app/admin/dashboard/page.tsx` — four metrics, an all-participants table, a recent
activity table, and a notes/messages table.

## Deliverables

1. **Summary metrics** — participant count, funding allocated, funding spent, and items
   needing follow-up, each for a selected fiscal year (default current). Every number comes
   from an API aggregate; no client-side summing across a table.
2. **Participant roster** — participant, client code, funding, spent, available, follow-up
   flag. Rows link to FE-10. Search and filter belong to FE-09; here the table is the
   first page of the same data, with a "view all participants" link instead of duplicating
   controls.
3. **Recent activity** — newest first, from `audit_events`: time, actor, action, entity
   type, and a link to the related record when one exists. `safe_details` is JSONB; render
   only the fields the API exposes, never raw JSON in the UI.
4. **Follow-up inbox** — expenses with `review_status` of `pending` or `needs_correction`,
   missing receipts, and open notes, with owner and status. Clicking an item opens the
   review screen (FE-11) or the participant workspace, per item type.
5. **States** — empty database (the honest first-run state: zero participants, zero
   funding), error with retry, loading skeleton per panel, and partial failure where one
   panel errors without blanking the rest.
6. **Fiscal year switch** — one control at the dashboard level, applied consistently to all
   panels and reflected in the URL.

## Data

- `GET /api/v1/participants?status=&cursor=` — roster page.
- `GET /api/v1/audit-events?entity_type=&cursor=` — activity feed.
- `GET /api/v1/participants/{id}/balances?fiscal_year=` — detail figures used by panels.
- `GET /api/v1/dashboard/summary?fiscal_year=` — proposed aggregate; confirm in API-01.

## Out of scope

- Editing anything from this screen.
- Notifications, messaging, or email. "Notes & messages" means internal follow-up records,
  not a chat product.
- Charts or analytics beyond the four figures listed.

## Acceptance criteria

- With an empty database, every panel shows a genuine empty state and no invented numbers.
- The roster's funding/spent figures match the same participant's figures in FE-10 for the
  same year.
- Activity entries carry actor and timestamp and link to an existing record; an entry whose
  record was hard-deleted renders without a broken link.
- Follow-up count equals the number of rows in the inbox for the same filters.
- The page renders for an admin only; a worker is redirected by the server guard.
- No participant name or amount from source documents appears in fixtures.

## Verification

`npm run lint`, `npm run typecheck`, `npm run build`. Manual against a local API seeded
with synthetic data: empty, one participant, many, one failing panel, and a worker trying
the URL directly.
